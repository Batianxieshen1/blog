两周合了 14 个 PR：
我不是在刷格子，是在建一条流水线

找 AI 产品方向的实习，需要能拿出来的公开证据。我选了开源贡献这条路，两周合了 14 个 PR，覆盖字节跳动、阿里巴巴、蚂蚁集团、CNCF、Grafana Labs。这篇不讲我有多努力，讲我怎么选仓库、怎么避开那些看起来很美实际进不去的坑，以及踩了三次的 DCO。

找实习的人很多。简历上写「熟练使用 Python/SQL」，写「做过电商增长分析」的人也很多。但简历上写着「向 CNCF 顶级项目 etcd 提交了 Go 安全升级，已被合并」的人不多。

这不是 LeetCode 能替代的。LeetCode 证明你能在隔离环境里写算法；开源证明你读懂了别人的代码、找到了问题、按项目的规范改了、让维护者认可了。这四步里每一步都比写算法难，而且全有据可查——PR 就在那里，谁都能看到。

我给自己定的规则：不交没验证过的改动。每个 PR 都先在本机复现问题、写回归测试、跑通之后再提交。这条规则让我多花了很多时间，但也让我避开了「提了但被维护者打回」的最坏结果。

01不要急着找 issue，先选对仓库

90% 的 PR 被拒不是质量问题，是选错了仓库。

我最初的直觉是找星标最高的项目，后来发现这个方向完全是错的。星标高只说明项目火，不代表它收外部人的 PR。

我写了一套筛选流程，用 GitHub GraphQL API 扫了 96 个仓库：

  • 拉取每个仓库近 90 天的合并记录
  • 剔除机器人和仓库成员，只统计独立外部贡献者的数量和合并速度
  • 按两个指标排序：独立作者数 × 中位合并时间
  • 逐个读 LICENSE 原文核实许可证

这个流程给我两个关键指标：独立作者数和中位合并时间。前者反映社区厚度，后者反映维护者响应速度。

数据陷阱

serverless/serverless 是一个 47k 星的项目，中位合并只要 2 小时，看起来非常好。但我拆开看发现：90 天内合并的 50 个外部 PR 里，没有一个是首次贡献者——全是老面孔。它的「快」是给内部人的快，你提了也不会有人看。

还有更极端的：PaddleOCR 和 MinerU 近 90 天分别收了 23 个和 56 个外部 PR，合并数为零。连 typo 修复都不收。这两个仓库的 issue 列表看起来很热闹，但那是幻觉。

伪开源

GitHub 的许可证标签会骗人。我把 96 个仓库的 LICENSE 原文全部读了一遍，发现 4 个看起来开源但实际不是的：

  • n8n（208k★）：Sustainable Use License，只能「内部业务或非商业个人使用」
  • serverless/serverless（47k★）：LICENSE 文件内容是一个商业客户协议 PDF 的链接
  • XiaoMi/ha_xiaomi_home（22k★）：小米自定义许可，原文写明「仅限于非商业性目的使用」
  • lobehub/lobehub（83k★）：LobeHub Community License，衍生作品需商业许可

这些项目你能在 GitHub 上提 PR，但它们不满足 OSI 的开源定义。我全部剔除了。

02选 issue 比写代码更花时间

仓库选对之后，下一步是在里面找一个能动手的 issue。我用了三种策略：

策略一：修主分支 CI 红灯（最稳）

主分支的 CI 如果红了，说明有一个确定的问题等着被修。而且这种机会几乎没有竞争——大家都在盯着 issue 列表抢，但 CI 红灯不在 issue 列表里。

deer-flow（字节跳动 84k★）就是这么做的。我发现它的 Unit Tests 在 main 上红了，追查发现是 cargo 冷编译超时——沙箱里写死了 60 秒，但一个 loaded runner 的工具链启动加编译就超过了。我改成 180 秒，提交后 10 小时被合并。

方法有效性的关键：bug issue 当天就会被社区里的人抢走，但 CI 红灯挂了几个小时都没人管。

策略二：版本升级（最可复制）

etcd（CNCF 52k★）的 issue #22628 要把 Go 从 1.27.2 升到 1.27.3（修 CVE），涉及主仓库加 6 个子仓库的多个分支。我做了主仓库的 4 个分支，后来又补了 6 个子仓库的 11 个分支，一共 17 个 PR。这类改动的核心就是版本号替换，风险低、review 快——全部被合并了。

策略三：抢新鲜 bug（需要快）

字节 deer-flow 的 bug issue 出现当天就有 PR，等于在赛跑。ant-design 的 4 个新鲜 a11y bug 挂了两天也没人碰，但全部标着 unconfirmed——维护者还没确认，你修了可能白修。

我学到的是：新鲜但未被确认的 issue ≠ 好机会。要看这个仓库的 review 速度有多快，以及维护者是不是已经在处理了。

03不交没验证过的改动

每个 PR 走这个流程：

  1. 在本机复现问题。不是看 issue 描述就动手，是让 bug 在你自己的机器上跑出来。有时候 issue 描述是对的但代码已经变了，有时描述本身就是错的。
  2. 写回归测试。先确认测试在修复前失败（红了），修复后通过（绿了）。如果写不出红绿，说明你还没理解问题。
  3. 修复 + 跑通所有已有测试。确保没有引入新的回归。
  4. 用真实的工具做基准。比如我在修 grafana 的 .gitignore 处理时，不是照 spec 写代码，而是建了一个临时 git 仓库跑 git check-ignore 来拿真实的基准。

这个流程让我在多个 PR 里避免了「修好了但引入了新 bug」的情况。比如 FunASR 那个 PR，我改了一行（int16 → int32），然后跑了 3000 组随机输入的对比，证明正常范围的行为逐位不变。

04踩过的坑（这是文章最核心的部分）

1. DCO 三连踩

etcd 要求每个 commit 带 Signed-off-by。我因为用 GitHub API 直接建 commit（不走 git），连续踩了三次：

  • 第一次：忘了加 Signed-off-by 行
  • 第二次：加了，但 author 的邮箱是 QQ 邮箱，Signed-off-by 用的是 GitHub noreply 地址。DCO 要求两者一致，所以还是 fail
  • 第三次：换了脚本又忘了加

教训：用 API 建 commit 时，signoff 行必须写在 message 模板里，不能建完再补。author 和 committer 的邮箱也必须显式指定为同一个地址。

2. 时区陷阱

我的测试在本地永远通过，CI 永远失败。追了两天才发现：测试夹具里写死了 -8 hours（我的时区 UTC+8），CI runner 是 UTC，算出来的日期差了一天。

修复方法是改用 SQLite 的 'utc' 修饰符，替代硬编码的时区偏移。验证方法是 TZ=UTC 前缀跑全量测试——如果你不知道这个方法，可以在自己的 Windows 机器上模拟 CI 的时区。

3. Git Bash 路径转换

我用 Git Bash 在 PR 下评论了 /retest，结果发出去的内容是 C:/Program Files/Git/retest。Git Bash 会把以 / 开头的字符串当成路径，自动加上 Git 安装目录前缀。

修复方法是 --body-file 从文件读内容，绕过路径转换。这个坑让我的一条 PR 重跑命令静默失败了好几个小时。

4. gh api -f 会把数组转成字符串

用 GitHub API 的 Tree API 时，tree 和 parents 字段需要传数组。但 gh api -f 会把它们序列化成 JSON 字符串，GitHub 返回 422 Invalid request。

修复是用 --input 从 JSON 文件传完整 payload，而不是用 -f 逐个传参数。

06给想开始的人的建议

  • 不要从 Linux Kernel 或 Kubernetes 开始。太大了，review 周期以月计。
  • 先扫再选。用数据找「合并快 + 收个人 + 真开源」的交集。星标数不是指标——serverless 47k 星你进了也白进。
  • 小 PR 大价值。一个带回归测试的 bug 修复 > 十个 typo 修复。前者证明你理解了问题并且能写测试，后者只证明你会打字。
  • 方法论比数量重要。能讲清楚「为什么选这个仓库、这个问题」比「我提了 100 个 PR」更有说服力。面试时被问到「最近在做什么」，你要能从「我怎么筛仓库」讲到「我怎么复现 bug」再到「我怎么验证修复没有引入新问题」——这条线讲下来，面试官看到的不只是代码，是你的工程思维。
